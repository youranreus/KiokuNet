# 升级到 Node / Knowledge Space 模型

本次是配置版本 1 → 2 的破坏性升级。先完成仓库构建与测试，再安排已有节点升级；新程序不会在启动时自动移动旧数据。

向各机器的执行 Agent 交接 1.0.0 升级时，分别使用以下说明；其中包含全网停服/恢复条件、使用方适配和验收要求：

- [Hub 升级执行说明](upgrade-1.0.0-hub.md)：包括本次 Hub 的 Hermes 整理流程、独立状态目录、指纹脚本和 MCP 重新授权。
- [普通节点升级执行说明](upgrade-1.0.0-node.md)：按本机实际空间和安装方式执行，包含 virtues-mini 的已核验示例。

## 预览

在每台机器使用原安装根执行：

```sh
kioku upgrade plan --home /absolute/original-install --json
```

预览不修改文件。输出网络 ID、目录移动、入口目标变化、将撤销的静态密钥 ID 和 OAuth 连接名称。保留网络/设备身份、空间归属、当前知识与同步文件夹 ID。

主要变化：

- `data/agents/<id>/raw/` → `data/spaces/<id>/`。
- 原 raw 入口改指空间本体；Shared 入口保留相同读写用途。
- 原 allRaw 入口改指全部空间只读副本，布局为 `<入口>/<id>/`。已有脚本须去掉末尾 raw 层。
- 旧静态密钥、OAuth 连接失效并重新授权。
- 未消费的旧节点邀请、旧签名迁移材料不能继续使用，升级后重新签发。
- 原目录旁的其他文件保留，空的旧父目录不自动清理。知识内容和用户的忽略规则不重写。

## 执行

先停止所有节点的服务，以及会直接写入知识的程序。核对预览、受影响连接和备份策略后，在每台机器执行：

```sh
kioku upgrade apply --home /absolute/original-install --confirm NETWORK_ID
```

工具检查本机 worker 和 Syncthing 已停止，不会替你停止它们。新 CLI 的 `service stop` 仍可停止旧配置或迁移中断的安装，其他常规命令拒绝使用未迁移的配置。迁移使用目录 rename，已有目标、被替换的链接、变化的配置或不安全路径会拒绝覆盖。

旧配置保留在 `config/config.v1.backup.json`，旧 OAuth 状态保留在 `config/oauth.v1.backup.json`。这些是含私密授权信息的迁移材料，使用 0600 权限，不放进空间或 Shared。工具不声称提供知识内容历史备份。

所有节点完成升级后再启动服务；重新生成邀请和 MCP 授权。不要让旧版本后台继续写新路径，也不要混用两个协议版本。升级不会自动启动服务或登录远程服务器。

## 中断恢复

`config/upgrade-v2.json` 保存恢复日志。在日志完成前，普通命令与 worker 拒绝启动；修复报告的问题后，重复相同 apply 命令恢复。

已移动目录通过文件系统身份验证，不再次复制或覆盖。已更新入口可重复检查，未更新入口继续处理。若配置或目录被外部替换，停止并核对，不删除日志强行重来。

升级完成后重复 apply 返回完成状态。保留日志和备份供人工核验；回退需要协调全部节点的服务、配置、目录和授权，不支持只恢复 config.json 就运行旧程序。
